# F11 v1：按 concept level 分组执行的单卡逻辑原型

日期：2026-10-23。状态：REPORTED；获批范围的实现和正确性结果见 [F11 结果报告](../results/F11-v1.md)。

用户明确选择：“同时实现单卡两组逻辑原型并验证正确性，多卡性能后续实测”。本文件记录该授权下的具体实现范围；不把它扩展为多 GPU 部署、CUDA Graph、动态 batching 或硬件租用授权。

## 1. 功能与场景

将一批请求的 11 个 concept levels 分为 A、B 两组。每个 level 都经过共享 Transformer 的完整 12 个网络层。在 A 完成后显式交接状态，B 继续生成，再用全部 codes 重建最终 latent 并输出 token IDs。

WMT14 的长度依次为 `[1,4,8,14,20,26,32,40,48,56,64]`。默认分界 `split=5` 表示 A 运行前五个 levels（至长度 20），B 运行剩余六个；这仅是正确性验证的固定分界，尚未证明其最优。

当前每个请求固定一个 batch，组内逐 level 执行；单张卡上的两组共用模型权重。支持先执行请求甲的 A，再执行请求乙的 A/B，最后恢复甲的 B，检验状态和随机数隔离。没有声称在一张 GPU 上实现两组并行。

## 2. 问题与源码证据

冻结上游：`c70274273f489abc73832b2b98584a8483b6b203`。`models/next_concept.py::generate` 将 prefix embedding、level0、后续 level、采样状态集中在一个不可暂停的调用中。后续循环中的 `z_hat` 尚未包括最后采样的 level，故暂停状态必须同时保留累计 latent 和已生成 codes，最终仍按原入口从全部 codes 重建。

现有 F00 性能记录存在梯度模式、源码冻结和探针方法问题，不能据此认定短层是 launch-bound、长层是 compute-bound，也不能选择最优切分。固定 prompt 长度为 96；实际 eager stack 输入为 96（level0）或 `96+L`，不能只按 target 的 1–64 长度推断成本。

## 3. 研究依据

[DistServe 原论文](https://arxiv.org/abs/2401.09670) 将 AR prefill/decode 分开分配资源，并考虑带宽和阶段 SLO。可借鉴阶段独立配置和公平资源对照；NCM 没有同样的逐 token decode 或稳定 TTFT/TPOT，采用 time-to-final-output。

[NCM 官方介绍](https://hazyresearch.stanford.edu/blog/2026-10-12-ncm) 描述 coarse-to-fine concept 生成；本方案是对其阶段执行的工程探索，不宣称研究首创或直接继承其他系统的加速数字。

## 4. 本轮方案

- `LevelGroups(runtime, split)`：单设备、固定 batch、WMT14 风格 predict-level0 eager RoPE。
- `submit`：验证配置与非空 prompt，生成本请求的 prefix embedding、padding bias、level encoding 和独立 CPU/CUDA RNG。
- `short_group`：顺序运行 A 的 levels；`handoff`：克隆快照，转移唯一有效状态的所有权，旧状态作废。
- `long_group`：按原顺序完成 B；从全部 codes 重建，运行 decoder/argmax；完成后移除注册状态。
- `cancel`：取消请求并释放执行器持有的状态引用；拒绝过时对象、错误模型标识、重复活动 ID、错误组次序。

请求状态含 batch ID、模型/配置指纹、CFG、next_level、prefix embedding、padding、累计 latent、全部已采样 codes、CPU/CUDA RNG。快照使用独立 tensor storage。当前 handoff 是同一设备上的逻辑复制，不是网络传输，不能报告跨卡带宽。

## 5. 边界

不训练模型，不改上游生成实现。CFG=0/1，FP32，固定同一 batch 划分。query-level0、上下文编码器、非 RoPE、flex attention 显式拒绝；不复用已有有缺陷的 KV 路径。

暂不实现跨请求合批、动态 A/B 资源配比、CUDA Graph、kernel 优化、真实多 GPU 传输、缓存共享。用户设想中的策略分别属于后续独立机制。较短层用更大 batch、较长层用更小 batch 仍是待测假设。

## 6. 文件与回退

隔离分支 `codex/f00-v1` 下新增 `benchmarks/e2e/level_groups.py`、`evaluate_groups.py`、`tests/debug/test_level_groups.py`。接口为显式实验 API 与独立 CLI，不改生产默认行为；回退为直接使用原始 `net.generate`。

## 7. 正确性约束

prompt/target mask、RoPE 重置、head 索引与上游一致；每个请求 levels 必须恰好执行一次、保持顺序。恢复时使用本请求的 RNG，执行后恢复进程原 RNG；CFG null 分支与 level-dependent 权重公式相同。所有离散 codes/IDs 必须精确一致；最终 latent 的容差固定 `atol=1e-4, rtol=1e-3`。不通过时保留失败，不放宽门槛。

## 9. 实验与性能验证

本轮执行正确性实验；GPU 进程 wall time 仅用于预算，不作为性能结果。后续多 GPU 性能实验需新批准和硬件：

1. 固定相同 GPU 数（至少两张）、精度、权重、数据、输出长度、采样质量；对比同资源完整实例数据并行与 A/B 分组，不能用两卡对单卡宣称收益。
2. 先扫全部十个分界、batch 组合和 A:B 卡数比例，包含不分离作为候选；成本包含排队、handoff、序列化、传输、重建和最终 decoder。
3. open-loop 固定到达 trace，负载为参考饱和能力的 0.25/0.5/0.75/1.0/1.25 倍，加一次突发；time-to-final-output p50/p95/p99、完成吞吐、goodput/GPU、失败率和峰值显存分别报告。
4. 用验证集选择分界，用保留测试 trace 评价；稳定 warmup 后至少五个交错顺序独立窗口，每窗至少 10,000 请求再讨论 p99。
5. 真实传输另测 payload/带宽；单卡或人工传输延迟只能标 SIMULATED。CUDA Graph、合批等每次只加一个机制做消融。

SLO 必须在多卡实验前确定，当前不虚构阈值。不同 batch 下浮点形状和 RNG 消耗变化须单独质量验证。

## 10. 成功与停止

本轮成功为上述支持范围正确性通过且保留完整输出。GPU 超时、OOM、任何离散不一致立即停止并保存已有记录。原型通过不等于生产就绪或分组提升性能。多卡性能待测。

## 11. 预算

复用现有环境、WMT14 与 tokenizer，新增下载 0；新增代码/原始数据预期 <100 MiB，仍受原 20 GiB 总磁盘上限约束。单张现有 RTX 4060，单模型副本，B=4。

用户明确追加：“批准追加最多 15 GPU 分钟用于正确性验证”。验证 supervisor 对完整 GPU 子进程设置 840 秒硬超时（含加载），留 60 秒用于修复后短验证；不运行完整性能矩阵。无云费用或新增卡。

## 12. 风险

暂停/恢复代码复制了部分上游执行控制流，未来上游变更必须重新核对，不能默认兼容。状态对象不是不可信网络消息格式；没有分布式容错、并发线程安全或批内请求取消支持。状态中的 mutable tensors 仅由执行器拥有；调用者不得自行修改。
